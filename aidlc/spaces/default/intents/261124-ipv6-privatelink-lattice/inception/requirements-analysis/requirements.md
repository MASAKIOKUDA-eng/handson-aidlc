## 意図の分析

- **目的:** 新しく作るサービス間通信の方式として、AWS PrivateLink と Amazon VPC Lattice のどちらを採用するか。方式を最終的に決める顧客側の担当者が、その判断に使える材料を作る（インテントステートメント）。
- **成果物:** 検証シナリオの文書。作成者以外の人も、この文書だけを見て、記載どおりの構成・手順・測定方法・記録方法で検証を実施できること（インテントステートメントの成功指標）。
- **種類:** 新規作成の文書。AWS 上では実行しない。
- **規模:** 経路 2 つ × 観点 3 つ（遅延、アクセス制御、呼び出し元の識別）。単一アカウント、単一リージョン。

## 公式情報の確認結果（2026-11-24 時点）

| 項目 | 確認結果 | 扱い |
|------|----------|------|
| PrivateLink の提供側 NLB | デュアルスタックが必須。IPv6 のみのサブネットには作れない。ターゲットは IPv6 のみのサブネットに置ける | 決定 D-16 に従い、NLB のサブネットのみデュアルスタックにする（FR1.2） |
| PrivateLink の利用側エンドポイント | IPv6 のみのサブネットに、IP アドレスタイプ IPv6 のインターフェイスエンドポイントを作れる | IPv6 のみで構成する |
| Fargate | ECS のドキュメントでは IPv6 のみの構成に対応（プラットフォームバージョン 1.4.0 以降）。ECR のデュアルスタックエンドポイントが必要で、ECS Exec は使えない。VPC の対応表には「非対応」の記載が残っている | 事前確認の手順を入れる（FR1.4） |
| VPC Lattice | IPv6 のターゲットグループを使える。IPv6 のみの VPC からの呼び出し（VPC の関連付け）は、公式情報どうしで記載が食い違っており確定できない | 事前確認の手順と、成り立たない場合の分岐を入れる（FR1.3） |
| Lattice での呼び出し元の情報 | ターゲットに届く送信元 IP は Lattice 側の管理プレフィックス（リンクローカル）。呼び出し元の VPC などはヘッダーで渡される（ヘッダー名は情報源によって表記が異なる） | 実施時に確認する項目として扱う（FR6.3） |

## 機能要件

文書（検証シナリオ）が満たすべき内容を、機能要件として定義します。

### FR1 前提と検証環境の構成

- **FR1.1** 文書は、検証環境の前提を一覧で示すこと。前提は次のとおり。
  - 同じアカウント内の 2 つの VPC で、どちらも IPv6 のみ（制約 C-T1、C-T4）
  - リージョンは東京（C-T5）
  - 呼び出し元は EC2 インスタンス（C-T2）
  - 呼び出し先は Fargate 上の ECS サービス（C-T3）
  - プロトコルは HTTP/1.1 の REST（Q1）
  - TLS は経路の途中で終端する（Q2）
  - 合否: 前提の一覧に、これらがすべて書かれていること。
- **FR1.2** 文書は、IPv6 のみにできない部分を明記すること。PrivateLink 提供側の NLB を置くサブネットは、IPv4 を併用するデュアルスタックにする。そのことと理由（NLB はデュアルスタック必須）を、構成の説明と結果の記録欄の両方に書く（決定 D-16）。
  - 合否: 構成の説明と結果の記録欄の両方に、例外とその理由が書かれていること。
- **FR1.3** 文書は、構築を始める前に、VPC Lattice が IPv6 のみの VPC からの呼び出しに対応しているかを確認する手順を含めること。対応していない場合は、利用側 VPC の該当部分をデュアルスタックにして続ける分岐と、その旨の記録方法を書くこと（決定 D-16、RAID R2）。
  - 合否: 確認手順と、対応している場合・していない場合の両方の分岐が書かれていること。
- **FR1.4** 文書は、Fargate を IPv6 のみで動かすための事前条件と確認手順を含めること。事前条件は次のとおり。
  - プラットフォームバージョン 1.4.0 以降
  - ECR のデュアルスタックエンドポイントからイメージを取得する
  - ECS Exec が使えないことを前提にする
  - 合否: 3 つの事前条件と確認手順が書かれていること。
- **FR1.5** 文書は、2 つの経路それぞれの構成図を含めること。図は Mermaid 形式で書き、テキストでの説明も併記する。
  - 合否: 経路ごとに図とテキスト説明があること。

### FR2 PrivateLink 経路の構築手順

- **FR2.1** 提供側の構成手順を含めること。
  - ECS サービスを、IPv6 のターゲットグループで NLB に登録する
  - NLB はデュアルスタックにし、TLS リスナーで TLS を終端する（Q2）
  - 提供側の NLB からエンドポイントサービスを作り、IPv6 に対応させる
- **FR2.2** 利用側の構成手順を含めること。利用側 VPC の IPv6 のみのサブネットに、IP アドレスタイプ IPv6 のインターフェイスエンドポイントを作り、EC2 から呼び出せるようにする。
- **FR2.3** 各手順に、次の 3 点を書くこと: 事前条件、操作、期待する結果。期待する結果は、画面やコマンドの出力で確かめられる形で書く。
  - 合否（FR2 全体）: 呼び出し元 EC2 から、PrivateLink 経由で ECS サービスに HTTPS で接続し、応答を確認する手順まで書かれていること。

### FR3 VPC Lattice 経路の構築手順

- **FR3.1** 次の構成手順を含めること。
  - サービスネットワークを作る
  - 利用側 VPC をサービスネットワークに関連付ける
  - HTTPS リスナーで TLS を終端する Lattice サービスを作る（Q2）
  - IPv6 のターゲットグループで ECS サービスを登録する
- **FR3.2** 各手順に、FR2.3 と同じく、事前条件・操作・期待する結果を書くこと。
  - 合否（FR3 全体）: 呼び出し元 EC2 から、Lattice 経由で ECS サービスに HTTPS で接続し、応答を確認する手順まで書かれていること。

### FR4 遅延の測定手順

- **FR4.1** 測る値は、確立済みの接続（キープアライブ）を使ったときの、リクエスト送信から応答受信までの往復時間とすること（Q3）。
- **FR4.2** リクエストは 1 件ずつ順番に送ること。同時に複数送る負荷はかけない（Q5）。
- **FR4.3** 2 方式で次の条件をそろえる手順を書くこと。
  - 同じ EC2 インスタンス
  - 同じアベイラビリティーゾーン
  - 同じ ECS タスク数とサイズ
  - 同じリクエスト内容と応答サイズ
  - 測定する方式の順番を交互に入れ替える
  - 測定する時間帯をそろえる
- **FR4.4** ウォームアップのリクエスト数、本測定のリクエスト数、繰り返しの回数を、具体的な数値で書くこと（値は NFR Requirements で決める）。
- **FR4.5** 結果として記録する値を、方式ごとに次のとおりとすること: 中央値、90 パーセンタイル、99 パーセンタイル、最小値、最大値、エラー件数。あわせて、2 方式の差（中央値と 99 パーセンタイル）を記録する欄を設けること。合否の判定は行わない（Q4）。
- **FR4.6** タイムアウトやエラーになったリクエストの扱いを書くこと。遅延の集計から外し、エラー件数として別に記録する。

### FR5 アクセス制御の検証手順

Q6 で選ばれた 3 つの仕組みについて、方式ごとに検証手順を書きます。

- **FR5.1** ネットワークのレベル（セキュリティグループなど）: 許可した呼び出し元からは応答が返り、許可していない呼び出し元からは接続できないことを確かめる手順。
- **FR5.2** 経路のポリシー: 許可された呼び出し元は通り、許可されていない呼び出し元は拒否されることを確かめる手順。対象は、PrivateLink のエンドポイントポリシーと、VPC Lattice の認証ポリシー。一方の方式でその仕組みが使えない場合は、「使えない」ことを比較結果として記録すること。
- **FR5.3** 接続の承認: 提供側が承認または関連付けをするまで、呼び出し元から接続できないことを確かめる手順。対象は、PrivateLink の接続承認（承認を必須にする設定）と、VPC Lattice のサービスネットワークへの関連付け。
- **FR5.4** FR5.1〜FR5.3 の各手順に、「許可される場合」と「拒否される場合」の両方を含めること。それぞれ、期待する結果（応答の HTTP ステータス、接続できないこと、タイムアウトなど）を書く。
  - 合否（FR5 全体）: 3 つの仕組みすべてについて、方式ごとに許可と拒否の両方のケースが書かれていること。

### FR6 提供側での呼び出し元の識別の検証手順

- **FR6.1** 呼び出し先の ECS サービスは、受け取った情報を応答とログに出す検証用アプリとすること。出す情報は、接続元の IP アドレス、Proxy Protocol の情報、受信したリクエストヘッダー。文書には、そのアプリの仕様を書く（Q7）。
- **FR6.2** PrivateLink: 次の 2 つの場合を比べる手順を書くこと。
  - NLB のターゲットグループで Proxy Protocol v2 を有効にした場合。アプリが呼び出し元の IPv6 アドレスと VPC エンドポイント ID を受け取れるかを確かめる。
  - 無効にした場合。アプリに見える接続元 IP がどうなるかを確かめる。
- **FR6.3** VPC Lattice: アプリに見える接続元 IP（Lattice の管理プレフィックスのアドレスになると想定）と、呼び出し元の VPC などを示すヘッダーを、アプリで確かめる手順を書くこと。ヘッダー名は実施時に公式ドキュメントで確認する。
- **FR6.4** 結果を、「アプリが受け取れる情報」の比較表に記録する欄を設けること。行は情報の種類（呼び出し元 IP、呼び出し元 VPC、エンドポイント／サービスネットワーク）、列は方式とする。
  - 合否（FR6 全体）: 両方式について、アプリで確かめる手順と比較表があること。

### FR7 結果の記録とまとめ

- **FR7.1** 遅延、アクセス制御、呼び出し元の識別のそれぞれについて、結果を記入する表のひな形を含めること。
- **FR7.2** IPv6 のみの構成から外れた部分（FR1.2、FR1.3 の分岐）を、結果の欄に記録できるようにすること。
- **FR7.3** 検証後に作成したリソースを削除する手順を含めること。

### FR8 参考情報

- **FR8.1** 手順の根拠とした AWS 公式ドキュメントへのリンクを、手順の近くと文末の一覧の両方に書くこと。
  - 合否: 各手順の近くと文末の一覧の両方に、リンクがあること。

## 非機能要件

- **NFR1 第三者による実施可能性:** 各手順に、事前条件・操作・期待する結果が書かれていること。前提知識として求めるのは、リンク先の公式ドキュメントと AWS の基本操作（コンソールまたは AWS CLI）だけにする。合否: 全手順にこの 3 点が書かれていること（インテントステートメントの成功指標）。
- **NFR2 再現性:** 遅延の測定条件をすべて具体的な値で書くこと。対象は、インスタンスタイプ、アベイラビリティーゾーン、タスクのサイズと数、リクエストと応答のサイズ、リクエスト数、繰り返し回数。合否: 条件の欄に空欄がないこと。
- **NFR3 測定の公平性:** 2 方式で条件をそろえる手順（FR4.3）が書かれていること。合否: FR4.3 の 6 項目がすべて書かれていること。
- **NFR4 セキュリティ:** 文書に認証情報、アカウント ID、証明書の秘密鍵を書かないこと（プレースホルダーで示す）。権限は、検証に必要な最小限にすること。合否: 文書に該当する文字列がないこと。
- **NFR5 情報の正確さ:** AWS の仕様に関する記述には、公式情報へのリンクと確認日を付けること。確認できていない点は「要確認」と明記すること。合否: 仕様に関する記述すべてに、リンクまたは「要確認」があること。
- **NFR6 期限:** 文書は 1 週間以内に完成させること（制約 C-O1）。

## 制約

- 成果物は文書のみ。AWS 上での実行は行わない（C-S1）。
- 比較の観点は、遅延、アクセス制御、呼び出し元の識別に限る（C-S2）。
- 呼び出し元の識別は、ネットワーク上の情報を対象とする（C-S3）。
- 同じアカウント、東京リージョン、IPv6 のみ（例外は FR1.2、FR1.3 による）。
- 作成者 1 人で、期限は 1 週間以内。

## 前提

| ID | 前提 | 理由 |
|----|------|------|
| AS1 | 検証用アプリは、文書の仕様に従って実施者が用意する（コードは成果物に含めない） | プランでコード生成を省いており、成果物は文書のみのため |
| AS2 | 呼び出し元の EC2 と ECS タスクは、同じアベイラビリティーゾーンに置ける | 遅延の比較条件をそろえるため（FR4.3） |
| AS3 | TLS の証明書は、実施者が用意したもの（ACM で発行したものなど）を使う | 証明書の発行方法は比較の対象外のため |
| AS4 | 遅延の差が小さい場合は、測定のばらつきの範囲と区別できないことがある。そのため、繰り返しの回数と値のばらつきも記録する | 合否を付けずに値を記録する方針（Q4）でも、判断材料として使えるようにするため |

## 対象外

- AWS 上での実行と、実測値（C-S1）
- 可用性、スケーラビリティ、運用のしやすさ、料金などの観点（C-S2）
- IAM の身元（プリンシパル）による呼び出し元の識別（実現性 Q6）。ただし、アクセス制御で使う Lattice の認証ポリシー（FR5.2）は対象
- 同時リクエストによる負荷をかけた状態での遅延（Q5）
- 新しい接続を作る時間を含む遅延（Q3）
- 検証用アプリのコード、構築用のスクリプトや IaC の作成（AS1）

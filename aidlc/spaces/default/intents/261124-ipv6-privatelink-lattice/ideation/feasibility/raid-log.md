# RAID ログ（リスク・前提・課題・依存関係）

インテントステートメント（`ideation/intent-capture/intent-statement.md`）と実現性評価（`feasibility-assessment.md`）をもとに整理しました。

## Risks（リスク）

| ID | リスク | 影響 | 可能性 | 対応 |
|----|--------|------|--------|------|
| R1 | PrivateLink の提供側（Network Load Balancer）を IPv6 のみのサブネットに置けず、提供側 VPC に IPv4 が必要になる | 高: 「IPv6 のみ」の前提を提供側で満たせない | 未確認 | 要件分析の前に公式ドキュメントで確認する。成立しない場合は I1 で扱いを決める |
| R2 | VPC Lattice が IPv6 のみの VPC からの呼び出し、または IPv6 のターゲットに対応していない | 高: Lattice 側の比較が成立しない | 未確認 | R1 と同じく確認する |
| R3 | 両方式で、提供側が受け取れるネットワーク情報（送信元 IP、VPC、エンドポイント）が大きく異なり、同じ基準で比較できない | 中: 識別の合否基準を方式ごとに書き分ける必要がある | 未確認 | 要件分析で、比較項目を「受け取れる情報の一覧」として定義する |
| R4 | AWS 上で実行しないため、シナリオの手順の誤りが、文書を使う人が実施するまで見つからない | 中: 第三者が実施できる水準（成功条件）を満たせない | 中 | 各手順に期待する結果を書き、公式ドキュメントの該当箇所を参照として記載する |
| R5 | 未確認点の確認に時間がかかり、1 週間の期限に間に合わない | 中 | 低〜中 | 確認項目を R1〜R3 に絞り、最初に確認する |

## Assumptions（前提）

| ID | 前提 | 確認方法 |
|----|------|----------|
| A1 | Fargate のタスクを IPv6 のみのサブネットで動かせる | 公式ドキュメントで確認する |
| A2 | PrivateLink のインターフェイスエンドポイントを IPv6 のみのサブネットに作れる | 公式ドキュメントで確認する |
| A3 | 遅延の比較では、呼び出し元・呼び出し先・アベイラビリティーゾーンなどの条件を 2 方式でそろえられる | 要件分析と非機能要件のステージで条件を定義する |
| A4 | 同じアカウント内であれば、アカウントをまたぐ共有の設定は不要 | 公式ドキュメントで確認する |

## Issues（課題）

| ID | 課題 | 担当 | 期限 |
|----|------|------|------|
| I1 | R1・R2 が現実になった場合に、「IPv6 のみ」の範囲をどう扱うか（提供側だけ IPv4 を許すか、対象から外すか）を決める | 顧客側の担当者（範囲の決定者） | 確認結果が出た時点 |

## Dependencies（依存関係）

| ID | 依存先 | 内容 |
|----|--------|------|
| D1 | AWS の公式ドキュメント | 両方式・ECS・Fargate の IPv6 対応範囲と、提供側が受け取れる情報の確認に使う |
| D2 | 顧客側の担当者 | 範囲の判断（I1）と、方式の最終決定 |

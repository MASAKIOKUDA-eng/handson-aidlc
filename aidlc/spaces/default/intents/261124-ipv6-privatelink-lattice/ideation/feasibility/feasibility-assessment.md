# 実現性評価: IPv6 VPC 間の ECS サービス呼び出し経路（PrivateLink 対 VPC Lattice）検証シナリオ

## 入力

- インテントステートメント（`ideation/intent-capture/intent-statement.md`）: 新しく作るサービス間通信で PrivateLink と VPC Lattice のどちらを採用するかを判断するための検証シナリオを、第三者も実施できる水準で作る。観点は遅延とセキュリティ（アクセス制御と、提供側での呼び出し元の識別）。AWS 上での実行は行わない。
- 実現性の質問への回答（`feasibility-questions.md`）: Q1〜Q8
- 市場調査（market-research）はこのプランでは実行していないため、入力はありません。

## 確定した前提（質問への回答）

| 項目 | 内容 | 出典 |
|------|------|------|
| IP アドレスの構成 | IPv6 のみ（IPv6-only サブネット、IPv4 は使わない） | Q1 |
| 呼び出し元 | Amazon EC2 インスタンス | Q2 |
| 呼び出される側 | AWS Fargate で動く Amazon ECS サービス | Q3 |
| VPC の配置 | 同じ AWS アカウント内の 2 つの VPC | Q4 |
| リージョン | 東京（ap-northeast-1） | Q5 |
| 呼び出し元の識別で求める情報 | ネットワーク上の情報（送信元 IP アドレス、VPC、エンドポイントなど） | Q6 |
| 規制・社内基準 | 特になし | Q7 |
| 期限 | 1 週間以内に文書を仕上げる | Q8 |

## 技術的な実現性

**結論: 文書としての検証シナリオは作成できる。ただし、「IPv6 のみ」の条件を両方式が満たせるかには未確認の点があり、次の段階で公式ドキュメントを確認する必要がある。**

AWS 上で実行しないため、この評価で言う「実現性」は次の 2 つです。

1. 検証シナリオの文書を、期限内に第三者が実施できる水準で書けるか
2. シナリオに書く構成が、両方式で成立する見込みがあるか

1 は実現できると判断します。比較の観点が 2 つに絞られていること、構成が単一アカウント・単一リージョンであること、規制による制約がないことが理由です。

2 については、次の点が未確認です。いずれも仮説として扱い、要件分析より前に AWS の公式ドキュメントで確認します（RAID ログ R1〜R4、A1〜A4）。

| 確認すべき点 | 影響 | 現時点の扱い |
|-------------|------|-------------|
| PrivateLink の提供側で使う Network Load Balancer を、IPv6 のみのサブネットに置けるか | 置けない場合、提供側 VPC に IPv4 を含むサブネットが必要になり、「IPv6 のみ」の前提を提供側で満たせない | 仮説（未確認） |
| PrivateLink のインターフェイスエンドポイントを、IPv6 のみのサブネットに作れるか | 作れない場合、呼び出し元 VPC も IPv6 のみにできない | 仮説（未確認） |
| VPC Lattice が、IPv6 のみの VPC からの呼び出しと、IPv6 のターゲットへの転送に対応しているか | 対応していない場合、Lattice 側の比較が成立しない | 仮説（未確認） |
| Fargate のタスクを IPv6 のみのサブネットで動かせるか | 動かせない場合、呼び出される側の前提が成立しない | 仮説（未確認） |
| 各方式で、提供側がどのネットワーク情報（送信元 IP、VPC、エンドポイント）を受け取れるか | 識別の比較項目と合否基準の書き方が決まる | 仮説（未確認） |

## 遅延の比較についての実現性

- AWS 上で実行しないため、この成果物には実測値が含まれません。シナリオには、測定の方法・条件・回数・集計方法・合否の判断基準を書き、実測は文書を使う人が行います。
- 2 方式を公平に比べるには、同じ呼び出し元（EC2）、同じ呼び出し先（Fargate 上の ECS サービス）、同じリージョン・アベイラビリティーゾーンの条件をそろえる必要があります。条件のそろえ方は要件分析と非機能要件のステージで決めます。

## セキュリティの比較についての実現性

- アクセス制御は、両方式とも AWS の設定（ポリシーやセキュリティグループなど）で行うため、シナリオで「許可された呼び出し元は通り、許可されていない呼び出し元は拒否される」ことを確かめる手順を書けると判断します（具体的な仕組みは要件分析で確定）。
- 呼び出し元の識別は「ネットワーク上の情報」に絞りました（Q6）。IAM の身元による識別は比較の対象外です。各方式で提供側が受け取れる情報の違いは、未確認の点として上の表に挙げています。

## 総合判断

| 観点 | 判断 |
|------|------|
| 文書の作成 | 実現可能 |
| 「IPv6 のみ」での両方式の成立 | 未確認（前提が崩れた場合の対応を RAID ログに記載） |
| 期限（1 週間以内） | 実現可能。ただし未確認点の確認に時間がかかると余裕が減る |
| 規制による制約 | なし |

## Assumptions & Open Questions

- 上の表の「仮説（未確認）」の各項目は、AWS の公式ドキュメントで確認するまで事実として扱いません。
- 前提が崩れた場合（たとえば提供側で IPv4 を含むサブネットが必要な場合）に、「IPv6 のみ」の範囲をどう扱うかは、確認結果が出た時点で判断します（RAID ログ I1）。

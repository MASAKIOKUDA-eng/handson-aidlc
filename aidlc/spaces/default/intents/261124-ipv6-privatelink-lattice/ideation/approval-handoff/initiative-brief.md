# イニシアチブ概要: IPv6 VPC 間の ECS サービス呼び出し経路（PrivateLink 対 VPC Lattice）検証シナリオ

構想段階の成果物（`intent-statement.md`、`stakeholder-map.md`、`feasibility-assessment.md`、`constraint-register.md`、`raid-log.md`）と、この段階の質問への回答（`approval-handoff-questions.md`）を 1 枚にまとめたものです。

## 目的と課題

- 新しいシステムで使うサービス間通信の方式として、AWS PrivateLink と Amazon VPC Lattice のどちらを採用するかを判断するための材料が必要です（`intent-statement.md`）。
- このため、IPv6 を前提とした VPC から別の VPC にある Amazon ECS サービスを呼び出す経路について、両方式を比較する検証シナリオの文書を作ります。
- 比較の観点は次の 2 つです。
  - 遅延
  - セキュリティ（アクセス制御と、提供側で呼び出し元を識別できるか）

## 市場の裏付け

市場調査のステージは実行していません。社内向けの技術検証であるため、調査の対象となる市場がないと判断しました。

## 実現性とリスクの要点

`feasibility-assessment.md` と `raid-log.md` をもとにまとめています。

- **文書を作れるか:** 作成できます。比較の観点が 2 つに絞られていること、構成が単一アカウント・単一リージョン（東京）であること、規制による制約がないことが理由です。
- **最大のリスク（R1、R2）:** PrivateLink の提供側（Network Load Balancer）と VPC Lattice が「IPv6 のみ」の構成に対応しているかが、まだ確認できていません。要件分析の前に、公式ドキュメントで確認します。
- **対応しない場合の扱い（課題 I1、決定済み）:** 成り立たない部分だけ IPv4 を併用（デュアルスタック）し、そのことを明記したうえで比較します（Q2）。
- **遅延について:** AWS 上では実行しないため、実際の測定値は含みません。シナリオには、測定方法と合否の判断基準を書きます。

## 範囲

`constraint-register.md` の内容です。

| 区分 | 内容 |
|------|------|
| 対象 | 呼び出し元は Amazon EC2、呼び出し先は Fargate 上の ECS サービス。同じアカウント内の 2 つの VPC で、どちらも IPv6 のみ。リージョンは東京 |
| 比較する経路 | AWS PrivateLink と Amazon VPC Lattice |
| 比較の観点 | 遅延、アクセス制御、提供側での呼び出し元の識別（ネットワーク上の情報） |
| 対象外 | AWS 上での実行。遅延とセキュリティ以外の観点（可用性、スケーラビリティ、運用のしやすさなど） |

範囲定義のステージは実行していません。範囲は、インテントステートメント、制約一覧、この段階の回答で決まっています。

## 体制

- 文書は、作成者 1 人で作成します（Q3）。期限は 1 週間以内です（制約 C-O1）。
- 方式の最終決定と、範囲・優先度の決定は、顧客側の担当者が行います（`stakeholder-map.md`）。
- 顧客側の担当者とは、目的と範囲について合意済みです（Q1）。
- 進捗は週 1 回報告します。

## Go / No-go の判断

**Go**（Q4）。RAID ログに記載したリスク（R1〜R5）とその対応を確認したうえで、要件定義（Inception）に進みます。

## 次の段階への引き継ぎ事項

1. 要件分析の前に、「IPv6 のみ」への対応状況（R1、R2、A1、A2）を AWS の公式ドキュメントで確認する。
2. 対応していない部分があれば、その部分だけデュアルスタックにして、文書に明記する（Q2）。
3. 両方式で、提供側が受け取れるネットワーク情報の違い（R3）を、比較項目として定義する。

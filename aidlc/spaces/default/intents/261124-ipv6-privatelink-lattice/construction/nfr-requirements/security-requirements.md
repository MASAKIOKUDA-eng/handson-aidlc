## 秘密情報と権限（NFR4）

| ID | 要件 | 合否の基準 |
|----|------|-----------|
| NFR4.1 | 文書には次の情報を書かず、`<ACCOUNT_ID>` などのプレースホルダーで示す。<br>・認証情報<br>・アカウント ID<br>・証明書の秘密鍵<br>・実際のドメイン名 | 文書に該当する文字列がない |
| NFR4.2 | 実施者に必要な IAM ポリシーの例を載せる（Q5）。<br>・対象サービス: EC2、Elastic Load Balancing、VPC Lattice、ECS、ECR、ACM、Route 53、CloudWatch Logs<br>・ECS のタスク実行ロールに限定した `iam:PassRole`<br>・`aws:RequestedRegion` で ap-northeast-1 に限定する<br>・`"Action": "*"` は使わない | ポリシー例にリージョンの限定と PassRole の対象限定があり、すべての操作を許可する指定がない |
| NFR4.3 | 両方式とも、自分で決めたドメイン名で呼び出す（Q6）。<br>・名前解決: Route 53 のプライベートホストゾーンで、AAAA で引ける別名（エイリアス、または CNAME）を作る<br>・証明書: その名前の ACM 証明書を使う（DNS 検証用に、公開 DNS で検証できるドメインが必要）<br>・使う場所: PrivateLink は NLB の TLS リスナー、Lattice はカスタムドメインの HTTPS リスナー | 手順で、呼び出す名前・証明書・名前解決の結果（AAAA）を確認している。証明書の検証を無効にする指定（`-k` など）を使っていない |
| NFR4.4 | 測定や確認で、実際の業務データを使わない | 文書の前提に明記されている |

## アクセス制御の検証（FR5、レビュー R-05 への対応）

「拒否される呼び出し元」として、利用側 VPC に、別のセキュリティグループを付けた EC2 をもう 1 台置きます（以下「拒否用 EC2」。Q4）。同じ VPC からでは区別できない仕組みは、設定の前後の状態を比べて確かめます。

| ID | 仕組み | PrivateLink の確認方法と期待する結果 | VPC Lattice の確認方法と期待する結果 |
|----|--------|-------------------------------|-------------------------------|
| NFR4.5 | ネットワークのレベル（FR5.1） | エンドポイントのセキュリティグループで、許可用 EC2 のセキュリティグループからの 443/TCP だけを許可する。許可用 EC2 は HTTP 200 が返り、拒否用 EC2 は接続がタイムアウトする | サービスネットワークと VPC の関連付けに付けるセキュリティグループで、同じ設定にする。期待する結果は PrivateLink と同じ |
| NFR4.6 | 経路のポリシー（FR5.2） | 自前のエンドポイントサービスで、エンドポイントポリシーが使えるかを、先に公式ドキュメントで確認する（要確認）。使えない場合は「使えない」と記録して終える | 認証ポリシーで、許可用 EC2 の IAM ロールだけを許可する。署名付きのリクエスト（curl の `--aws-sigv4`）で確かめる（要確認）。許可用 EC2 は 200 が返り、拒否用 EC2 と署名なしのリクエストは 403 が返る |
| NFR4.7 | 接続の承認（FR5.3） | エンドポイントサービスを「承認が必要」に設定し、次の 3 つの状態で接続を確かめる。<br>・承認前: 接続できない<br>・承認後: 200 が返る<br>・拒否した後: 接続できない | VPC の関連付けについて、次の 3 つの状態で接続を確かめる。<br>・関連付けの前: 名前解決または接続ができない<br>・関連付けの後: 200 が返る<br>・関連付けを外した後: 接続できない |

## 呼び出し元の識別の想定結果（FR6、レビュー R-02 への対応）

呼び出し先のアプリには nginx を使います（詳細は `tech-stack-decisions.md`）。応答に、アプリから見えた値を返させます。

| ID | 確認項目 | 想定する結果 | 想定と違う場合 |
|----|----------|-------------|----------------|
| NFR4.8 | PrivateLink、Proxy Protocol v2 有効 | `proxy_protocol_addr` が、呼び出し元 EC2 の IPv6 アドレスになる。`proxy_protocol_tlv_aws_vpce_id` が、利用側エンドポイントの ID（`vpce-` で始まる）になる | 実際の値をそのまま記録し、「想定外」と書く |
| NFR4.9 | PrivateLink、Proxy Protocol v2 無効 | `remote_addr` は NLB の IPv6 アドレスになり、呼び出し元は分からない | 同上 |
| NFR4.10 | VPC Lattice | `remote_addr` は Lattice の管理プレフィックスのアドレスになる（要確認）。ヘッダー `x-amzn-source-vpc` が、利用側 VPC の ID になる（ヘッダー名は要確認） | 同上。ヘッダーがない場合は、受信したヘッダー名の一覧を記録する |
